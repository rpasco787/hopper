Drain (1 broker, 8 workers x 16, PIN=1, 300 B, 384m limit):
- Java cold throughput / Go cold throughput: 0.25, because the Java worker
  spends about 25x Go's CPU per job (interpreted and C1 code early, grpc-java
  and protobuf allocation, a virtual thread and a Heartbeat object per
  delivery), and eight JVMs share the workers' 3 CPUs, so Java is CPU-bound
  where Go is bound by the broker and PostgreSQL.
- Java warm throughput / Go warm throughput: 0.40. C2 halves Java's per-job
  CPU once warm, but it stays CPU-bound on 3 CPUs; Go's warm pace is near its
  cold one.
- Worker CPU per 1,000 jobs, cold: Go 130 ms, Java 1,800 ms (JVM start and JIT
  amortized over a drain of WARM_JOBS + 40,000 jobs).
- Peak RSS per worker: Go 22 MiB, Java 140 MiB. Threads per worker: Go 9,
  Java 26.
- Startup to an accepted stream: Go 120 ms, Java 1,500 ms (eight JVMs starting
  at once on 3 CPUs, slower than the smoke's two).
- Saturation: yes. The workers' 3 CPUs saturate under Java for the whole
  drain; under Go they don't.
Steady (1,000 jobs/s after a 60 s warm-up):
- Pickup p99: Go 6 ms, Java 12 ms. End-to-end p99: Go 20 ms, Java 60 ms.
  kept_up for both: yes (warm Java needs about 1.2 of the 3 CPUs at 1,000/s).
- Worker CPU per 1,000 jobs, warm: Go 200 ms, Java 1,200 ms.
10,000 handlers on one worker (1g limit):
- Peak RSS: Go 110 MiB (10,000 goroutines with grown stacks, timers and
  per-delivery state), Java 300 MiB (virtual thread stacks live in the heap,
  plus grpc-java per-message buffers; heap 768 MiB, so not near the limit).
  Threads: Go 12, Java 30.
- jdk.VirtualThreadPinned events in the Java proof run: about 50, all in the
